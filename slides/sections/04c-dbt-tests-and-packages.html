you could also automate checks for data quality

    data tests

    • assertions you make about your model.
    • a way to confirm that your outputs and inputs are as expected.
    • implemented as generic (column-level) tests or singular (model-level) tests.

    unit tests

    • validate small portions of your functional code.
    • validate your SQL modelling logic on a small set of static inputs.
    • typically, you want to test both probable scenarios and edge cases.

            every test is a query you pay for, so start with the keys

            how dbt Labs tells its AI agents to rank data tests, from its agent skills

            always

            unique and not_null on the primary key. relationships on foreign keys. a broken key breaks every join below it.

            when the data shows it

            accepted_values on a column with a known set. not_null where you checked there are no nulls.

            sometimes

            accepted_range on bounded numbers. expression_is_true for a rule across columns.

            avoid

            not_null on every column. many expression_is_true tests on one model.

            • test data quality in staging, keys wherever a join changes the grain, and business rules in marts.
            • to check that your SQL logic is right, write a unit test instead.
